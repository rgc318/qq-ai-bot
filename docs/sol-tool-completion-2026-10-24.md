# Sol 图片工具空收尾诊断

事件发生于 2026-10-24 晚间；诊断与 1.7.1 部署完成于 2026-10-25 凌晨（Asia/Shanghai）。

近期一次群内改图已成功上传参考图并发送生成图片，但 Sol 的三个文字收尾请求均结束为空，随后切到 DeepSeek 1017 完成反馈。需要区分人格配置、业务提示词、LiteLLM、CLIProxy 和上游模型的影响。

## 已确认的缺陷与触发条件

AstrBot 在 `# Persona Instructions` 段尾追加原生工具回复规则，包含 `never return an empty response`。User Policy 的人格替换正则会替换这个标题直到下一个一级标题或文本结束，将这段原生规则一起删除。

已通过真实原生构建与有序回调验证，未依赖对源码的猜测：

| 阶段 | 核心工具回复规则 |
| --- | --- |
| 原生 request 创建后 | 存在 |
| 表情包与记忆请求钩子后 | 存在 |
| User Policy 应用人格后 | 消失 |
| 修复后的本地兼容插件最终钩子后 | 恢复 |

但规则被覆盖不是全部解释。对同一历史与准备好的系统提示词进行对照，单独补回原生英文工具规则仍会空完成；明确要求图片成功交付后用一句自然文字反馈，才使该复现恢复。

原提示词与 Sol 接入链的工具回合结束行为存在兼容问题：`tool_choice=auto` 时，这份上下文可稳定得到空消息、`finish_reason=stop`、输出计数为 4；相同上下文禁用后续工具选择，或明确图片完成后的文字收尾要求，能够得到正文。

## 排查边界

通过响应头确认，Sol 经过 LiteLLM → CLIProxy；DeepSeek 的上游是 SiliconFlow。直连 CLIProxy 后，Chat Completions 和 Responses 均能复现空完成。流式 Responses 也没有文字 delta，完成事件中的文字长度仍为 0。没有发现“CLIProxy 已返回正文但被 LiteLLM、SDK 或 QQ 发送层丢弃”的证据。

这定位了可验证的请求触发条件和本地提示词兼容缺陷，不代表已读取 CLIProxy 内部对上游服务的原始流，也不能断言官方模型内部究竟为何产生空回合。没有修改 CLIProxy 或 LiteLLM 服务端源码。

不能将 DeepSeek 的表现解释为“人格本身更正确”：生产中接管收尾的 DeepSeek 沿用的仍是龙娘人格，只是那轮返回了文字。这几轮观测显示两个接入链对工具完成后的回应行为不同，不能推广成 DeepSeek 从不超时或出错。旁路直接拼装历史的 DeepSeek 图像对照还曾返回 400，不把它作为严格等形的模型优劣证据；本结论依赖原生生产记录和 Sol 自身的受控对照。

OpenAI Docs 对原生 Sol 的工具调用仍要求 Responses；当前 Chat Completions 是本部署的代理兼容路径。本次两种协议均复现，因此只换协议不足以解决该问题。[官方模型说明](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

## 实现

本地插件 1.7.1 在最终 `on_llm_request` 钩子恢复核心工具规则，追加独立的 `# QQ Tool Response Rules` 标题，避免后续人格段替换误吞。

若本轮提供绘图/自拍工具，则追加条件式收尾规则：只有工具明确确认成功下发且数量大于 0，才按真实结果用当前人格简短反馈；不要套固定话术，不重复绘图或发送，不编造生成图中的细节。失败、零张或发送未确认不宣称成功；有其他待完成任务继续处理，遵从明确的输出格式要求。

没有更改模型绑定、`low` 推理、群权限、对话历史、引用图上传、超时或备用链。正常请求不强制 `tool_choice=none`，继续允许有必要的后续工具调用。不新增一次模型调用或固定等待，也不把所有空结果一律掩盖成成功。

## 授权与对照结果

用户明确允许仅在原容器内使用该次会话的 19 条历史、引用图与工具结果，向现有同机 CLIProxy/LiteLLM 作续答对照，并进一步允许只记录工具选择、绝不执行工具。诊断程序没有工具执行器；未调用生图接口、发送 QQ 或修改原会话。

这不是故障原始 HTTP 的逐字节重放：历史固定为已完成工具结果之前的存储样本，系统提示由原生构建和请求钩子准备；为隔离变量，审计关闭了额外近期快照、旧索引目录及图片任务事实注入。控制组与修复组使用相同历史、工具定义、推理档位及输出预算，差异为系统收尾规则。

| 同一历史的对照 | 结果 | 耗时 |
| --- | --- | --- |
| 修复前控制组，直连 Chat / auto | 空正文，4 输出 tokens | 3.24 秒 |
| 修复后，直连 Chat / auto | 正文 28 字符，无重复绘图调用 | 5.01 秒 |
| 修复后，LiteLLM Chat / auto | 正文 25 字符 | 5.33 秒 |
| 修复后，直连 Responses / auto | 正文 25 字符 | 5.13 秒 |
| 修复后，携带原会话请求头经 LiteLLM | 正文 25 字符 | 5.09 秒 |
| 将工具结果改为失败的反例 | 正文如实说明失败 | 4.44 秒 |
| 用户仍有历史查询任务的反例 | 继续选择记忆检索工具，未提前结束；诊断不执行它 | 4.45 秒 |

本组 Sol 输入由 8764 增至 8964 tokens，增加约 200。主要收益是避免该复现中的三次空输出重试和跨模型接管；不构成所有请求都固定 5 秒的保证。规则仍由模型执行，真实 QQ 新一轮仍需观察，不能承诺模型永不空返回。

7 项规则回归、50 项原路由回归，以及 17 项原生回调、26 项日志、15 项开工提示、12 项引用图、15 项群权限、旧对话索引/记忆工具检查通过。

## 数据与复现入口

完整会话导出最初被自动审批拦截，已停止并移除主机上的临时副本。真实样本调用同样在获得上述明确授权后才执行，全部留在原容器。结束后清理了容器内的会话、提示词、临时凭据副本和脚本，只保留脱敏统计；本机临时 API 凭据保留在被 Git 忽略的凭据文件中。

脱敏统计位于忽略的 `logs/tool-response-diagnosis-final.json`、`logs/native-tool-prompt-audit*.json`、`logs/tool-response-contract-native-verification.json`。代码入口：`tool_response_contract.py`、`scripts/test-tool-response-contract.py`；合成样本诊断为 `scripts/probe-tool-continuation.py`；获明确授权的容器内决策对照程序为 `scripts/probe-private-continuation.py`，它不包含样本、密钥或固定的真实会话 ID，也不会自动准备敏感数据。
