# 上下文插件冷启动加载失败与页面状态错误

## 已确认的两个原因

2026-10-29 当前进程日志中，15:44:46 本地插件 `1.11.5` 初始化失败。调用链为 `main.initialize → ContextRuntime.initialize → BackendCoordinator.switch`，异常为 `BackendUnavailable: 原生群历史注入接口未就绪`。随后该插件被移除。原生 `astrbot` 插件直到 15:44:47 才加载，用户插件先加载的实际顺序触发了这个问题。23:24 手动重载后已正常启用，说明只检查重载成功不足以验证冷启动。

页面还有独立的响应解析错误：当前 AstrBot 的 `PluginViewPage` 会把 `{status: 'ok', data: state}` 拆成 `state` 再交给 `apiGet/apiPost`。本地页面仍检查 `response.status === 'ok'`，把正常响应显示为“读取状态失败”，并保持切换按钮禁用。直接读取两个状态 API 均正常，因此该截图不能单独用于判断运行后端是否离线。旧页面回归只模拟外层包装格式，漏掉了实际的桥接格式。

Docker 标准输出包含大量早期诊断日志；本次故障依据为当前进程 `/api/v1/logs/history` 中的启动堆栈。原始日志仅保存到忽略目录，不提交聊天正文或凭据。

## 1.11.6 修复

- 冷启动保存 ContextAware 选择、保留插件及状态 API，原生群历史模块尚未加载时标记 `startup_pending`，通过 `on_plugin_loaded` 重新安装原生历史隔离钩子并恢复已保存后端。重复通知不叠加钩子，也不重新写入后端选择。
- 等待期间不把新消息悄悄交给不同的上下文后端；状态返回 `requested_backend`、`startup_pending` 和 `startup_issue`。源码缺失等情况可在页面明确选择本地后端恢复服务，选择会保存。
- 初始化出错时清理已安装的适配器。卸载时一个依赖清理失败也继续恢复其余补丁；ContextAware 清理异常仍释放归档维护工作和模块引用。
- 页面同时兼容原始状态对象及外层包装格式；状态格式、依赖等待和切换失败分别显示原因。GET 临时失败按 2/4/8…30 秒退避重试，页面离开时停止；正常状态不轮询。读取超过 10 秒显示超时，切换 POST 超时只重新读取状态，不自动重复提交修改。
- 页面脚本增加 `1.11.6` 缓存标识。修复不改变当前模型、人格、群权限、原消息或图片档案，不新增聊天模型调用或固定等待。
