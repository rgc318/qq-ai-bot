# 上下文后端接入与时延验证

日期：2026-10-25。版本：本地扩展 1.9.0。生产部署结论以 `STATUS.md` 最新记录为准。

## 使用与边界

在 AstrBot「插件 → QQ 人格模型与回复条件 → 上下文后端」选择「本地」或「ContextAware」。页面使用[官方插件页面 SDK](https://docs.astrbot.app/en/dev/star/guides/plugin-pages.html)，通过 AstrBot 已有登录身份访问接口，不另存 API Key。

同一请求只使用一个后端，切换保留群、成员策略、人格、模型、推理参数和共用档案。正在处理的消息持有后端代次；模型、图片工具、业镜排队/回复任务未结束时拒绝切换。业镜的常驻图片缓存清理循环不属于对话任务，不阻止切换。

ContextAware 固定为 MIT 的 3.11.0 / `f026c5635f49b43b18f2f4e53eefbc7a0180cd94`。运行目录保存原始 13 个源文件和 LICENSE，散列见 `integrations/contextaware/source-lock.json`。加载时只移除上游全局事件/工具注册装饰器，由本地适配层明确调用；上游源文件字节不变。没有同时注册第二套选图工具或修改 AstrBot 核心文件。

近期群聊注入由所选后端负责，ContextAware 模式跳过该群的原生重复注入和本地重复快照。原生消息收集保留，继续服务业镜与回退。传给主模型的是带消息 ID、发言者、时间、@、回复对象的可观察事实；上游规则推断的对象不冒充模型决策。接话判断仍沿用现有唯一判断流程，本次没有另加一个 ContextAware 判断模型。

## 消息、图片和文件

- 原始消息、经原生成功发送回调的文字回复、图片和文档仍使用已有 AttachmentStore；没有第二套持久化数据库。文字回复内部档案 ID 使用 `reply:输入消息ID:序号`，不伪装成 QQ 回执 ID。业镜直接发送的文字仍依靠既有 AstrBot 对话历史参与后续上下文，未另包裹其发送器。
- `browse_group_history` 支持关键词、发言者、引用目标、时间范围和游标翻页，包括只有图片、没有文字的消息。`read_group_message` 继续支持精确 ID/关键词回看。
- 模型通过 `view_context_images` 读取真实像素，使用明确的 `reference_ids` 选择最多 4 张参考；独立新图填 `[]`。可选 `reference_notes` 自由说明每张图的用途，交给万象画卷前转成按实际附图顺序排列的用途文字。
- 选择由模型根据语境完成，程序不写“三视图”“第二位成员”等场景分支。目录不等于像素，也不能保证模型每次都主动查全来源。
- 本轮可见资料固定在消息进入时的顺序边界内。思考期间新图不能偷偷加入；缓存淘汰后，本轮已授权图片仍从相同原档案读取。清空/人格或权限变化后拒绝旧快照。
- 生成仍走现有万象画卷正常工具，保留权限、额度、模型创作的开工对白和成功发送后的归档；没有额外生图模型或独立后台重放。
- 素材默认保留 24 小时、消息索引默认 7 天，仍受原容量和策略范围约束。图片过期后只能明确说明缺失。文字文档读取继续使用已有工具，视频/音频理解、额外视觉摘要和私聊话题笔记本次未启用。

## 失败处理与日志

日志在既有 trace、模型、Provider、用途字段之外附带 `backend` 和 `generation`；`context_backend_ready` 单独显示本地准备耗时，不把模型接口等待混算成业务开销。

图片接口明确返回 `moderation_blocked`、无效图片数据或 401/403 时，给模型具体失败原因，并从本轮实际原生执行器的工具集合移除图片工具，不再让模型反复尝试。每轮最多两次图片工具执行，允许一次瞬时失败重试；新用户请求单独计数。没有用另一节点绕过审核，也不承诺后台补发。

## 验证与延迟

使用当前 AstrBot 镜像、真实 SDK、与生产相同 Docker 数据卷上的独立空子目录；容器禁网、不挂真实历史/配置/密钥。约 30.1 MB 的合成历史图片保留在测试档案中。最后一次结果：

| 测量 | 本地 | ContextAware |
| --- | ---: | ---: |
| 普通文字样本 | 40 | 40 |
| 本地准备 p50 | 5.373 ms | 6.932 ms |
| 本地准备 p95 | 6.698 ms | 8.057 ms |
| 首次准备 | 6.698 ms | 43.738 ms |

p95 增量 **1.359 ms**，此前几轮约 1–4 ms。普通文字不新增模型、图片描述、摘要或固定静默等待。模型读取历史图/文件时存在必要的工具往返；更多相关事实也会增加输入 token，不能保证模型端延迟完全不变。

4 次纯文本合成接口对照（每路线/后端各一次）均正确综合三人的人数更改及地点保留：

| 路线 | 本地接口耗时 | ContextAware 接口耗时 |
| --- | ---: | ---: |
| DeepSeek 1017 | 6.903 s | 1.669 s |
| Sol low | 2.955 s | 2.882 s |

这些是少量单次样本，不能据此宣称 ContextAware 加快模型推理。输入分别约 568/1314 token（DeepSeek）及 878/1575 token（Sol）。只发送虚构群聊文字，没有真实会话重放、图片生成或 QQ 发送。

42 项原生检查覆盖单一工具注册、两张参考真实字节、缓存淘汰、成功结果去重及父图关系、切换恢复文字与图片、队列互斥、人格/清空隔离、历史分页和原生执行器停止重试，也验证了业镜直接启动模型后的任务退出清理、缓存事件复用和失败状态释放。另有 20 项附件存储、9 项协调器测试及插件页面 SDK 逻辑测试。页面视觉检查因应用内浏览器不可用未完成。

上线检查曾因业镜常驻缓存清理任务被误算为排队回复而触发回滚，旧配置和版本恢复检查通过；修正后往返切换通过。日志检查另发现旧开工对白验收替身缺少消息对象，已补齐替身及日志容错，日志回归增加后端/代次和简化事件检查。

报告在忽略的 `logs/context-runtime-volume.json`、`context-runtime-model-probe.json`、`context-runtime-deployment.json`。其中前两项为隔离验证，最后一项才记录实际部署结果。

## 复现与部署

```powershell
# 仅缺失时获取固定提交，校验 SHA-256；旧候选评估不等于部署
python scripts/evaluate-contextaware.py --download-source
# 禁网原生回归和同卷隔离基准，不调用模型
python scripts/evaluate-context-runtime.py --same-volume
# 可选：4 次合成纯文本接口对照，会使用既有 API
python scripts/evaluate-context-runtime.py --same-volume --models
# 初次迁移默认要求 1.8.1 基线；备份、空闲部署、回归和失败回滚
python scripts/deploy-context-runtime.py
# 已核查的 1.9.0 实例重新部署时，必须显式指定基线
python scripts/deploy-context-runtime.py --baseline 1.9.0
```

生产实例中 `_ca_runtime/` 由部署脚本从 `integrations/contextaware/` 打包；不要仅复制扩展目录或运行旧 1.8 安装脚本。再次升级需明确核查基线，不跳过安装器的版本检查。

全新安装使用 `scripts/install-local-bindings.py`，已改为递归打包页面及 `_ca_runtime/`；它拒绝覆盖已有运行实例。可先用 `--package-only` 离线检查 ZIP。尚未部署固定上游源码时，仅本地后端可用；获取固定源码并核查配置后，通过运行时部署脚本启用候选，不能只改模式文件。

首版仅测试群 347440128。此版本具备共同上下文、多成员来源和按需浏览，不等于已实现所有多话题独立任务排队、长工具后台调度或完全可靠的自主选图。复杂场景仍要根据真实使用中的来源日志与结果继续验收。
